# What is the Difference Between Star Schema and Snowflake Schema?

**Type:** Theoretical
**Topic:** Data Modeling, Dimensional Modeling

---

## The Question
> "Explain Star Schema and Snowflake Schema. When would you choose one over the other?"

---

## Core Difference

| | Star Schema | Snowflake Schema |
|---|---|---|
| Dimension tables | Denormalized (flat) | Normalized (split into sub-tables) |
| Joins required | Few — fact + dimension only | More — fact → dimension → sub-dimension |
| Query performance | Faster (fewer joins) | Slower (more joins) |
| Storage | More (duplicate values in dimensions) | Less (normalized, no duplicates) |
| Maintenance | Easier | Complex |
| Best for | OLAP, analyst queries, dashboards | Large dimension tables with many sub-attributes |

---

## Concrete Example — Same Data, Two Designs

**Scenario:** E-commerce orders with product and location data.

### Star Schema
```
           FACT_ORDERS
          /     |      \
    DIM_PRODUCT  DIM_DATE  DIM_LOCATION
```

```sql
-- DIM_LOCATION is flat — all attributes in one table
DIM_LOCATION(location_id, city, state, country, region, continent)

-- Query: no sub-joins needed
SELECT l.country, SUM(f.revenue)
FROM FACT_ORDERS f
JOIN DIM_LOCATION l ON f.location_id = l.location_id
GROUP BY l.country
```

### Snowflake Schema
```
           FACT_ORDERS
          /     |      \
    DIM_PRODUCT  DIM_DATE  DIM_CITY
                               |
                           DIM_STATE
                               |
                           DIM_COUNTRY
```

```sql
-- DIM_LOCATION is normalized into city → state → country
-- Query needs 3 joins to get country
SELECT c.country_name, SUM(f.revenue)
FROM FACT_ORDERS f
JOIN DIM_CITY ci    ON f.city_id = ci.city_id
JOIN DIM_STATE st   ON ci.state_id = st.state_id
JOIN DIM_COUNTRY c  ON st.country_id = c.country_id
GROUP BY c.country_name
```

## When to Choose Which

**Star Schema:**
- Analytical queries — speed matters, joins are expensive
- Business intelligence tools (Tableau, Power BI) — they work best with simple joins
- Snowflake, BigQuery, Redshift — columnar storage compensates for redundancy
- Default choice for most modern data warehouses

**Snowflake Schema:**
- Dimension table is very large with deep hierarchies (e.g., geography with 5 levels)
- Storage cost is a hard constraint
- Frequent updates to dimension attributes — normalization reduces update anomalies

**Real-world reality:** Most teams default to Star Schema. Snowflake Schema is chosen only when a specific dimension is enormous and deeply hierarchical.

---

## Fact Tables vs Dimension Tables

| | Fact Table | Dimension Table |
|---|---|---|
| Contains | Metrics / measures (revenue, quantity, clicks) | Descriptive attributes (name, category, city) |
| Grain | One row per event/transaction | One row per entity |
| Examples | FACT_ORDERS, FACT_PAGEVIEWS | DIM_PRODUCT, DIM_CUSTOMER, DIM_DATE |
| Key type | Foreign keys + degenerate keys | Primary key (surrogate) |

---

## How to Say It in the Interview
> "Star Schema denormalizes dimension tables — all attributes flat in one table. Snowflake Schema normalizes them into sub-tables. Star Schema is faster for queries because it needs fewer joins, but uses more storage due to repeated values. Snowflake Schema saves storage and handles update anomalies better but at the cost of join complexity. For modern cloud warehouses doing analytical workloads, I'd default to Star Schema — columnar storage and query optimizers reduce the storage concern, and analyst-facing queries are simpler."

## Follow-ups & Answers

**"What is a fact table grain?"**
> The grain defines what one row in the fact table represents — e.g., "one row per order line item" vs "one row per order". Deciding the grain is the first step in dimensional modeling. Fine grain = more rows, more flexibility; coarse grain = fewer rows, less detail.

**"What is a surrogate key?"**
> An artificial integer key generated by the warehouse (e.g., `product_key = 1, 2, 3...`) used in dimension tables instead of the source system's natural key. Insulates the warehouse from source key changes and enables SCD Type 2 history tracking.

**"What is a degenerate dimension?"**
> A dimension attribute stored directly in the fact table with no separate dimension table — e.g., `order_number` in FACT_ORDERS. It's a descriptor but has too many unique values to make a useful dimension.

## Common Mistakes
- Saying Snowflake Schema is always better (it's not — query performance suffers)
- Confusing Snowflake Schema with Snowflake the cloud DWH product (completely different)
- Not knowing what "grain" means — interviewers often ask this immediately after
