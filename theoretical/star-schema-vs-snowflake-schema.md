# What is the Difference Between Star Schema and Snowflake Schema?

**Type:** Theoretical
**Topic:** Data Modeling, Dimensional Modeling

---

## The Question
> "Explain Star Schema and Snowflake Schema. When would you choose one over the other?"

---

## Core Difference

| | Star Schema | Snowflake Schema |
|---|---|---|
| Dimension tables | Denormalized (flat) | Normalized (split into sub-tables) |
| Joins required | Few — fact + dimension only | More — fact → dimension → sub-dimension |
| Query performance | Faster (fewer joins) | Slower (more joins) |
| Storage | More (duplicate values) | Less (normalized) |
| Best for | OLAP, BI dashboards | Large dimensions with deep hierarchies |

---

## Concrete Example

**Star Schema — DIM_LOCATION is flat:**
```sql
DIM_LOCATION(location_id, city, state, country, region, continent)

SELECT l.country, SUM(f.revenue)
FROM FACT_ORDERS f
JOIN DIM_LOCATION l ON f.location_id = l.location_id
GROUP BY l.country
```

**Snowflake Schema — location split into sub-tables:**
```sql
SELECT c.country_name, SUM(f.revenue)
FROM FACT_ORDERS f
JOIN DIM_CITY ci   ON f.city_id = ci.city_id
JOIN DIM_STATE st  ON ci.state_id = st.state_id
JOIN DIM_COUNTRY c ON st.country_id = c.country_id
GROUP BY c.country_name
```

---

## When to Choose Which

**Star Schema:** analytics speed matters, BI tools (Tableau, Power BI), cloud DWH — default choice.

**Snowflake Schema:** dimension is very large with deep hierarchies, storage is constrained, frequent attribute updates.

**Real-world default:** Star Schema. Snowflake Schema only when a dimension is enormous and deeply hierarchical.

---

## Fact vs Dimension Tables

| | Fact Table | Dimension Table |
|---|---|---|
| Contains | Metrics (revenue, quantity) | Descriptive attributes (name, city) |
| Grain | One row per event | One row per entity |
| Keys | Foreign keys | Primary key (surrogate) |

---

## How to Say It in the Interview
> "Star Schema denormalizes dimension tables — all attributes flat. Snowflake normalizes them into sub-tables. Star is faster for queries (fewer joins) but uses more storage. For modern cloud warehouses doing analytical workloads, I default to Star Schema — columnar storage and query optimizers reduce the storage concern, and queries are simpler."

---

## Follow-ups & Answers

**"What is a fact table grain?"**
> What one row represents — e.g., one row per order line item. Deciding grain is the first step in dimensional modeling.

**"What is a surrogate key?"**
> Artificial integer key generated by the warehouse. Insulates from source key changes and enables SCD Type 2 history.

**"What is a degenerate dimension?"**
> Dimension attribute stored in the fact table with no separate dimension table — e.g., `order_number` in FACT_ORDERS.

## Common Mistakes
- Confusing Snowflake Schema with Snowflake the cloud DWH product
- Not knowing what "grain" means — interviewers ask this immediately after
- Saying Snowflake Schema is always better
